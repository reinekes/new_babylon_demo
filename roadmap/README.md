# Как пользоваться картой развития

Откройте index.html двойным щелчком. Всё необходимое встроено: интернет и установка библиотек для просмотра не нужны. Разделы: маршрут, открытый план, сделанное по датам, историческая сверка, библиотека исходных документов и эта инструкция. Таблицы можно искать и фильтровать по группе, статусу, приоритету и дате. Строки раскрываются: внутри фактическое состояние, следующий шаг, критерий завершения и источники.

## Что является источником истины

- plan.md — только незавершённые задачи, со стабильными ID и зависимостями.
- reports/YYYY-MM-DD.md — неизменяемая история. Несколько отчётов за день: YYYY-MM-DD-02.md, -03.md и далее.
- historical-review.md — проверка замечаний и научные оговорки.
- overview.md — последовательность развития и решения о приоритетах.
- index.html и snapshot.json — автоматически собранные копии. Не редактируйте их вручную.
- manifest.json — список Markdown для обновления через HTTP; создаётся сборщиком.

Исходные игровые документы не перемещены и не переписаны. В HTML встроена библиотека docs/**/*.md и основных документов игры. Личный new-babylon-case.md, музыка, бинарные файлы и сохранения сюда не включены. Это внутренний рабочий HTML: встроенные документы становятся доступны всем, кому вы передадите файл.

## Когда задача действительно завершена

1. Проверьте её критерий «Готово когда» и зависимости. Отметьте строку в HTML. Галочки сохраняются в этом браузере как черновик и сами не изменяют Markdown.
2. Нажмите «Экспорт» и укажите дату, фактическую версию/коммит, заметку о проверках. Для выбранной задачи нельзя оставить незавершённую зависимость вне выбранного набора.
3. Скачайте ZIP. В нём новый plan.md без выбранных записей и новый reports/дата.md с ID, исходными требованиями и вашей заметкой. Старые отчёты не удаляются. Экспорт не доказывает публикацию игры.
4. Распакуйте архив и скопируйте plan.md в эту папку, а отчёт — в reports/. Проверьте различия перед заменой. Исходный HTML не получает доступ к файловой системе автоматически.
5. Запустите ОБНОВИТЬ.command. Он пересоберёт HTML и откроет его. Если macOS не разрешает запуск файла, выполните в терминале из папки проекта: `python3 roadmap/build.py`.

При ручном редактировании работает тот же порядок: перенести полный пункт из плана в новый отчёт, перечислить ID в completed, оставить факт/проверки/ограничения. Зависимости могут ссылаться на выполненные ID из отчётов. Повторное закрытие и циклические зависимости сборщик не пропустит. Пока новые Markdown не загружены, старые галочки остаются черновиком.

## Как добавить задачу

Новый пункт должен иметь уникальный ID без пробелов. Метаданные идут сразу после заголовка; разделы — после них. Списки depends и sources разделяются точкой с запятой. Для пустого списка используйте дефис.

```md
## gfx-new-scene | Улучшить конкретную сцену
group: graphics
status: planned
priority: P2
depends: -
sources: GAME_DESIGN.md

### Описание
Конкретная проблема и желаемое поведение.

### Что уже есть
Проверенные факты, отдельно от предложения.

### Следующий шаг
Одно выполнимое действие.

### Готово когда
Наблюдаемый критерий и необходимые проверки.
```

Группы: graphics, simulation, godhood, economy, people, audio, ux, performance, reliability, history. Статусы: planned, partial, verify, decision. Приоритеты P0–P3. Источники — пути от корня проекта или HTTP(S)-ссылки. Файлы-источники должны существовать. Не меняйте ID при простом переименовании названия.

## Как добавить датированный отчёт

```md
## accepted-20261104-01 | Принят конкретный этап
date: 2026-11-04
type: completion
release: идентификатор-если-есть
commit: фактический-коммит-если-есть
publication: not_published
groups: graphics
completed: gfx-new-scene
source: -

### Изменения
Что теперь работает.

### Проверки
Сценарий, результат и фактические ограничения.

### Ограничения
Что ещё не принято или не опубликовано.
```

Для опубликованного игрового выпуска используйте type: release и publication: recorded только после фактического подтверждения, с источником docs/versions/дата.md. Значения pending и unknown означают отсутствие закрытого подтверждения в записи, а не необходимость повторно выпустить старую игру. Сведения о 44 старых выпусках перенесены из их документов; текущий публичный сайт этим аудитом заново не проверялся.

## Обновление и проверка

Сборка: `python3 roadmap/build.py`. Только проверка структуры: `python3 roadmap/build.py --check`. Проверки сборщика: `python3 -m unittest discover -s roadmap/tests`. Проверки браузерной логики: `node --test roadmap/tests/app.test.mjs` из корня проекта.

При открытии через file:// используется встроенный снимок. После правок Markdown пересоберите HTML. При просмотре через локальный HTTP-сервер кнопка обновления читает актуальные Markdown из manifest.json; новые файлы отчётов требуют пересборки manifest. Библиотека исходных документов обновляется только сборкой. Если загрузка или проверка не удалась, остаётся последний корректный снимок и появляется сообщение.

Дата плана — updated в plan.md. Дата отчёта — дата фактического действия, а не дата, когда идею придумали. CPU и FPS записываются отдельно. Изменения этой панели не являются игровым релизом и не требуют выдуманного номера версии или публикации Pages.

Библиотека сохраняет ранее опубликованные справочные тексты в document-archive.json, если их файлов больше нет в checkout. Архив не заменяет обязательные sources задач. Локальные docs/superpowers не добавляются в публикацию автоматически.
